# `@deepseek-ai/dsh-client-ui-voice`

English | [中文](README.zh.md)

The explicit `html[data-dsh-mobile]` entry uses the same Session speech profile and call lifecycle. Mobile captions include padding in their width and voice status text wraps within the composer; desktop geometry is unchanged.

Mobile greetings, call sentences, and committed-message audio download through same-origin page-authenticated fetch and play from local Blob URLs. Each mobile runtime reuses one gesture-unlocked media element across the greeting and subsequent replies; silent unlock audio never advances the call. Prefetch does not change the active source. Stop or cancellation releases each request and Blob URL without stopping another sentence. Download, HTTP authorization, invalid audio, and playback failures have separate diagnostics. Desktop playback retains progressive direct audio URLs. This does not bypass browser certificate trust or audio permissions.

Browser microphone input and committed-assistant speech controls over [`@deepseek-ai/dsh-speech-web`](../../speech/speech-web/README.md). The Node half is an empty roster plugin. The browser half registers a microphone in `conversation.input.right`, transient status in `conversation.composer.dock`, and a play/stop action in `conversation.chat.assistant-actions`.

The global client plugin renders no control until `voiceClient.profile(sessionId)` reports an operation authorized by that Session's live Agent scope. It does not infer capability from an agent-preset id. A connection reset refreshes cached profiles; leaving a Session stops microphone tracks, transcription, synthesis preparation, and media playback.

Customer-facing shells can request `ctx.voiceRuntime.create(session)` to render their own visual controls over the same recording and call controllers. This client service keeps cross-plugin collaboration behind Cordis injection. The returned runtime owns one Session and must be disposed when that surface unmounts; it preserves the same Host profiles, microphone lifecycle, call interruption, caption timing, and cleanup behavior as the standard slots.

Microphone capture negotiates the first Host-accepted `MediaRecorder` type supported by the browser and uploads one complete Blob. The recognized text is trimmed and appended to the existing draft on a new line. It remains editable and is not submitted automatically.

After transcription, the microphone becomes `Voice send` while the draft remains byte-for-byte equal to the text the control wrote and the Host profile also permits synthesis. Voice send synchronously arms the Session for one new committed assistant message before invoking the ordinary input submission action. The highest committed assistant seq forms the arm-time boundary, so remounted or later-paged history cannot claim the arm. A transcription-only profile shows `Send transcript` and submits without an arm. Ordinary Send never arms playback; editing the draft returns the control to microphone mode.

The finalized assistant action atomically claims an armed message and requests synthesis by `sessionId`, `messageId`, and the Host-authorized profile. Every playback label identifies the result as AI-generated speech. Desktop playback uses the returned same-origin URL directly, so a chunked audio response can begin before it completes. Mobile playback waits for the complete response, bounded by the Host synthesis output limit. A best-effort user-gesture unlock runs at Voice send, but autoplay rejection remains a normal playback error and leaves the same message's explicit retry button available. Manual play/stop remains available for every committed assistant message with synthesis capability.

## Voice calls

`VoiceCallView.messages` retains the current call's greeting, recognizer drafts, and generated answer rows with stable ids. Interruption marks the current answer without removing it; muted or abandoned drafts are marked unsubmitted. Starting another call resets this transient transcript. It is not a second model history: accepted messages remain in the ordinary Session, and the greeting adds no durable assistant event.

During audible playback, automatic interruption treats speech onset and initial partial text as a candidate rather than cancelling the answer. The Host-advertised `interruption` settings configure partial-transcript confirmation time, meaningful-text length, echo similarity, and short-backchannel bounds. The classifier combines ASR finality, sustained speech, normalized information and character diversity, question or correction form, short acknowledgement structure, and similarity to the active answer. A complete meaningful turn can interrupt immediately; a partial turn must remain meaningful through `confirmationMs`. Likely playback echo and passive acknowledgements are discarded without submitting a message. This is not a single interruption-word list. The configurable `utteranceMergeMs` then waits for adjacent accepted final segments, and a wordless onset renews that deadline without stranding the draft. A confirmed continuation carries the previous question into the next submitted text, followed by new segments in order. Pending segments accumulate while cancellation reaches idle. Completed answers end this carry-forward interval; later questions use normal Session history.

Alternate shells can call `setMuted(boolean)` to discard unfinished recognition and suppress outgoing microphone frames; unmuting waits for a new speech-start event before accepting recognition. Already uploaded audio cannot be recalled. `interrupt()` cancels the owned answer and playback without disconnecting recognition. Both operations are inert outside an active recognition loop; existing call controls and Host VAD defaults are unchanged.

When the Host advertises streaming recognition, synthesis, and `call` settings, the composer offers a full-screen call. After the fixed greeting ends, the microphone continuously sends mono 16 kHz PCM16 frames, including during assistant answers. The server returns live captions, detects speech onset, and finalizes segments after silence. The customer caption retains completed segments and appends the current partial result. Speech resumed within `utteranceMergeMs` cancels the pending handoff, so the complete accumulated text enters the ordinary Session as one user message. During audible playback, only a confirmed turn claim interrupts playback and cancels that answer; onset, likely echo, and passive acknowledgements do not. The selected fixed greeting preloads before the call and plays directly on click, while microphone setup runs concurrently. Automatic language selection uses the configured Cantonese greeting; recognized text then enters the ordinary Session reply-language policy. An explicit language selects its prepared greeting. Greetings add no model request or conversation message. The greeting is protected from recognition events: microphone frames are discarded locally until it ends, while hangup and service errors still stop playback. Speak after the greeting; speech during it is not transcribed. Customer transcript and assistant speech use separate labeled bubbles. Generated assistant text appears as its Session projection updates, independently from audio startup, so a delayed or failed provider does not leave the call screen blank. Call audio uses the Host’s `playbackRate` with pitch preservation. No send button is required.

Submitted messages are durable immediately through the normal conversation log. Closing the dialog does not copy or rewrite history. Hangup, Session switching, preset changes, and connection resets stop capture and playback and cancel the call's pending turn. A competing user message ends the call without cancelling that user's work. Calls require an idle ordinary Session with an empty queue. Recognition, microphone, and call-transport errors stop the loop. After the greeting, a sentence-synthesis or playback failure stops the current answer's remaining audio, shows a warning, and returns to listening without closing recognition. An unanswered turn has the Host-configured deadline.

Microphone access requires a secure browser context. Qwen recognition owns utterance detection; the browser uses the Host’s `microphone` processing options before recognition, `responseTimeoutMs` for answers, and `maxPendingAudioMs` for microphone uplink backpressure. Capture produces 100 ms frames. Only one audio upload is in flight; frames captured while it waits are coalesced into ordered uploads without a batching timer or discarded samples. Each request carries at most 64,000 bytes (two seconds), while queued and in-flight PCM may span the separately configured backlog interval. This lets a short transport or main-thread pause recover without making any request oversized. Exceeding the total interval ends the call rather than replaying an unbounded stale recording.

Calls extract sentences from live assistant text and start synthesis as soon as spoken punctuation is available. Sentence-ending punctuation always commits a segment; comma-like pauses commit only after `sentencePauseMinChars`, avoiding tiny standalone requests. Layout newlines do not end a spoken sentence. Segments containing no letter or number, such as a trailing standalone emoji, remain in text history but do not become synthesis requests. After the current sentence becomes audible, the queue prepares at most one next sentence while retaining ordered playback; it never opens speculative lookahead before current audio proves usable. When the Host advertises a fallback synthesis profile, a preferred-provider failure before audio begins retries the current sentence once and keeps the successful fallback for the rest of the call. Internal synthesis segments preserve their source whitespace without adding caption line breaks. `sentenceMaxChars` bounds unpunctuated segments; `sentenceQueueLimit` bounds pending audio. Interruption and hangup stop active and queued audio. The Host validates the logged text prefix and rejects stale text and reasoning. Already audible content cannot be retracted, and history does not represent playback progress.

## Model Experience

Indirectly, through the ordinary prompt submission the Voice send control dispatches: the Host speech package returns transcript text, while `ui-conversation` owns durable user-message admission. Recording, profile lookup, synthesis, and playback add no model-visible content.

#### KV Cache effect

Display and playback add no model tokens. Submitted transcripts are ordinary appended user messages; a continuation includes the interrupted question again in the new message, increasing its input tokens without rewriting earlier history.

## Known Limitations and Deferred Work

- **Speaker identity and unusual short turns** — interruption screening does not verify the speaker and is a deterministic transcript classifier rather than another model request. Meaningful bystander speech can still interrupt, while an uncommon one- or two-character correction without question or correction form can be ignored. Acoustic and language-specific device testing remains necessary.
- **Mobile startup latency** — each call sentence downloads completely before playback, not the whole answer. This can delay first sound compared with desktop progressive playback; one-sentence lookahead still overlaps the next download with current audio.
- **Idle-session voice send** — recording and Voice send are disabled while an earlier turn runs because the input action exposes no prompt-to-turn receipt; accepting queued voice input could otherwise let the earlier turn's committed reply claim the arm.
- **Complete-recording transcription** — MediaRecorder bytes cross the Host only after Stop; partial recognition and interruption-safe resumable uploads are unavailable.
- **Current-session playback** — switching Sessions stops audio instead of continuing it in the background.
